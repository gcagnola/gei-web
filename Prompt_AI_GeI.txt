Estamos trabajando en el proyecto **Laravel GeI — Guastavino e Imbert Administración**.

Antes de dar comandos o proponer cambios, respetá este contexto técnico y no supongas contenedores, rutas o herramientas diferentes.

## Estructura del proyecto

La raíz del proyecto es:

```text
~/proyectos/gei-web
```

El código Laravel está en:

```text
~/proyectos/gei-web/src
```

Docker Compose está en:

```text
~/proyectos/gei-web/docker-compose.yml
```

La carpeta `src` se monta dentro de los contenedores como:

```text
/var/www/html
```

## Comandos

Para Artisan usar siempre el alias:

```bash
gei-artisan ...
```

El alias equivale a:

```bash
docker exec -it \
    --user "$(id -u):$(id -g)" \
    -e HOME=/tmp \
    -w /var/www/html \
    gei-app php artisan
```

Ejemplos:

```bash
gei-artisan route:list
gei-artisan migrate
gei-artisan optimize:clear
```

Para npm y Vite usar `gei-node`:

```bash
docker exec -it gei-node npm install
docker exec -it gei-node npm run build
docker exec -it gei-node npm run dev -- --host 0.0.0.0
```

Para Composer usar `gei-app`, respetando UID y GID del usuario:

```bash
docker exec -it \
    --user "$(id -u):$(id -g)" \
    -e HOME=/tmp \
    -w /var/www/html \
    gei-app composer install
```

No crear contenedores temporales para Node, PHP o Composer sin revisar primero el `docker-compose.yml`.

## Convenciones de base de datos

Todas las tablas nuevas creadas para el sistema web deben comenzar con:

```text
web_
```

Todos los campos nuevos creados para el sistema web también deben comenzar con:

```text
web_
```

No renombrar tablas ni columnas heredadas.

No modificar estructuralmente tablas heredadas salvo agregar campos nuevos con prefijo `web_`.

Toda modificación de base de datos debe quedar documentada mediante migraciones o scripts SQL reproducibles.

## Forma de trabajo

Antes de indicar comandos:

1. Revisar en qué contenedor corresponde ejecutarlos.
2. No asumir que una herramienta está instalada en `gei-app`.
3. Usar `gei-artisan` para Artisan.
4. Usar `gei-node` para npm y Vite.
5. Explicar un paso por vez, porque el usuario está comenzando con Laravel y Docker.
6. No introducir Tailwind, Alpine.js, Livewire u otra tecnología sin justificarla y acordarla previamente.
7. No reemplazar Bootstrap mientras el proyecto lo siga utilizando.
8. No dar varios caminos alternativos cuando uno solo sea suficiente.
9. Pedir o revisar los archivos reales antes de modificar arquitectura, Docker o configuración.
10. Mantener las decisiones ya tomadas y señalar cualquier contradicción antes de avanzar.
